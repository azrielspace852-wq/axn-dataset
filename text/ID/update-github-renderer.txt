==================================================
3. SUPPORTED PROJECT STRUCTURES
==================================================

Support multiple ways of organizing HTML-based content.

A. SINGLE-FILE HTML PROJECT

Users may place all content inside one HTML file.

Example:

content/
└── my-animation/
    └── index.html

The HTML file may contain:

- Inline CSS inside <style>.
- Inline JavaScript inside <script>.
- HTML markup.

The renderer must discover and render this project automatically.

B. SEPARATED HTML, CSS, AND JAVASCRIPT

Users may organize their content into separate files.

Example:

content/
└── my-animation/
    ├── index.html
    ├── style.css
    ├── script.js
    └── assets/
        ├── background.png
        └── character.svg

The HTML document should be able to reference its CSS, JavaScript, images, fonts, and other local assets using relative paths.

C. MULTIPLE CSS AND JAVASCRIPT FILES

Also support projects containing multiple stylesheets and JavaScript modules.

Example:

content/
└── my-animation/
    ├── index.html
    ├── css/
    │   ├── reset.css
    │   ├── style.css
    │   └── animation.css
    ├── js/
    │   ├── main.js
    │   ├── animation.js
    │   └── effects.js
    └── assets/

The renderer must respect the references and loading order defined by the HTML document.

Do not assume that every project uses filenames such as style.css or script.js.

The HTML entry point should be configurable.

Default entry point:

index.html

Allow users to specify another HTML entry point when necessary.

7. ANIMATION TIMING AND FRAME SYNCHRONIZATION
==================================================

HTML-based animations must be rendered consistently at the requested FPS.

Do not rely entirely on uncontrolled real-time browser playback.

Investigate deterministic frame rendering.

For each frame:

1. Calculate the intended timestamp.
2. Advance the animation to the corresponding timestamp.
3. Allow required rendering and compositing operations to complete.
4. Capture the frame.
5. Submit the frame to the video encoding pipeline.

Evaluate suitable browser mechanisms such as:

- Page animation time control.
- requestAnimationFrame synchronization.
- CSS animation timeline control.
- Web Animations API.
- Virtual time or equivalent deterministic scheduling mechanisms.

Do not assume that simply waiting for a fixed number of milliseconds produces deterministic frames.

Avoid:

- Missing frames.
- Duplicate frames.
- Inconsistent animation speed.
- Timing drift.
- Uncontrolled playback speed.
- Capturing frames before the browser finishes rendering.

Support the requested FPS accurately.

For example:

30 FPS:
Frame 0 = 0 ms
Frame 1 = 33.333 ms
Frame 2 = 66.667 ms

60 FPS:
Frame 0 = 0 ms
Frame 1 = 16.667 ms
Frame 2 = 33.333 ms

The final video duration and frame count must be consistent with the selected configuration.

Document any browser animation features that cannot be controlled deterministically.

- Browser screenshot capture.

- Direct raw frame streaming.
- FFmpeg stdin.
- Backpressure.
- Buffer reuse.
- Memory consumption.
- Browser-to-Node.js data transfer.

Do not assume that browser screenshots can be converted to raw RGBA without decoding.

If screenshots are used:

- Avoid unnecessary disk writes.
- Avoid unbounded frame buffering.
- Process frames sequentially.
- Use appropriate image decoding.
- Preserve output quality.

If raw frame extraction is possible without compromising correctness, evaluate it.

Do not sacrifice visual accuracy for a theoretically faster pipeline.

The HTML rendering backend must integrate with the existing FFmpeg encoding architecture.

Keep the rendering pipeline modular so that both rendering modes can use shared video encoding components where appropriate.

12. RESOURCE MANAGEMENT
==================================================

Implement reliable resource management.

Ensure:

- Browser instances are not created unnecessarily.
- Pages and browser contexts are reused where safe.
- Temporary pages are closed.
- Browser processes are terminated after rendering.
- FFmpeg processes are cleaned up.
- Temporary files are removed.
- Memory does not grow continuously with frame count.
- Frames are processed sequentially or with strictly bounded concurrency.
- Failed renders do not leave orphaned browser processes.

Avoid launching one browser process per frame.

Use one controlled browser session per rendering job unless a different design is technically justified.

Implement proper cleanup for:

- Successful completion.
- Rendering errors.
- FFmpeg failures.
- Browser crashes.
- Timeouts.
- User cancellation.
- GitHub Actions termination where cleanup is possible.
